# Production deployment and monitoring

This procedure targets a Linux host with Python 3.12, Node 22, PostgreSQL 18, Nginx, and a process supervisor. It does not describe an existing deployment. Nginx/Docker are unavailable on the development machine; the supplied proxy template has not been syntax-tested or exercised with real certificates.

1. Check out the desired Git commit to `/srv/lossfit`. Install `backend/requirements.txt` into an isolated Python environment. Run `npm ci` and `npm run build` in `frontend/`.
2. Create a dedicated PostgreSQL application database and restricted application role. Store secrets outside the repository using `.env.production.example` as a field list. Replace every placeholder. Use separate generated JWT and stable deletion-ledger keys. Set explicit HTTPS origins, the exact Google callback if enabled, and an absolute private-upload directory owned by the API service user. Restrict the environment file to that user.
3. Back up the database and external deletion ledger using `docs/backup-restore.md`. With the deployment environment loaded, run `python -m alembic -c backend/alembic.ini upgrade head` from the repository root. Do not start multiple concurrent migration processes.
4. Start `python -m backend.run` under a supervisor with the repository as its working directory. This entry point requires production mode, binds to loopback by default, trusts only the configured proxy addresses, and disables raw Uvicorn access logs. Configure automatic restart, a dedicated non-administrator service user, and write access only to private storage. Keep the API port private.
5. Adapt `deploy/nginx.conf` for the real hostname, certificate paths, and frontend build directory. Run `nginx -t` before activating it. Only the frontend build directory is public; never serve the repository root or private uploads. TLS terminates at the proxy. Raw proxy logs are disabled because they may contain OAuth/reset tokens. If proxy diagnostics are enabled later, redact URLs, query strings, headers, and bodies before collection.
6. Verify HTTPS `/api/v1/health/live` and `/api/v1/health/ready`, cookie flags, registration/login/reset delivery, private-file authorization, scanner/chat integration, and the full acceptance workflows on the deployed origin. Record evidence. A successful build or local test does not establish deployed readiness.

## Monitoring

The API emits one JSON event per request to standard output: `event`, generated `request_id`, allowlisted HTTP `method`, registered route template (or `unmatched`), `status`, and `duration_ms`. It does not log raw paths, query strings, bodies, credentials, user identifiers, or exception messages. Handled unexpected failures return a generic error and request ID. A failure after response headers were sent is recorded as `request_failed`; the HTTP status may already be 200, so alert on that event as well as 5xx responses.

Forward these JSON events from the process supervisor to the chosen monitoring service. Alert on sustained `request_failed`/5xx rates, readiness failures, unusual latency, private-file cleanup backlog, and backup failures. Retain only operational metadata according to a documented retention policy. Provider credentials must remain in the backend secret store. No external monitoring account or alert destination is configured or verified here.

On an incident, correlate the user's `X-Request-ID` with the sanitized event. Reproduce in an isolated environment; do not enable request-body or exception-value capture against personal health data. Keep failed private-file cleanup jobs for retry, and verify restore/deletion-ledger replay before restoring traffic. Roll application code back only after checking schema compatibility; restore backups into an isolated target rather than overwriting the active database blindly.
