# Accessibility verification

The shared layout provides a keyboard-visible skip link, a focusable main landmark, focus transfer after navigation, current-page navigation announcements, and visible focus on links, buttons, inputs, selects, and textareas. Assistant access lives in the header so it does not cover scanner or form controls. Authenticated routes use a three-row app shell: the header and bottom navigation have their own rows, and the main region scrolls between them. This keeps the dock persistent without covering forms or scanner controls. Reduced motion is respected in the stylesheet.

## Automated evidence

`npm.cmd run test:e2e:local` passed all seven Chromium workflows on 2026-11-06. The navigation test uses deterministic API fixtures and runs axe WCAG 2 A/AA and WCAG 2.1 AA checks on login, catalogue, manual food entry, and the scanner unavailable state. It also signs in through the keyboard only by tabbing through the email, password, and submit controls, typing credentials, and pressing Enter; the test verifies focus begins on the main landmark. The authenticated database journey creates and persists a meal using only the keyboard: focus moves through meal details, search results, serving, amount, adding a food, and saving. The authenticated journey also runs axe on analytics, food detail, meal detail, scanner review, profile, and Help. No violations were reported on those states. The tests verify keyboard activation of the skip link, focus on main content, the catalogue navigation announcement, horizontal overflow in the scrolling main region at 320/390/720/768/1440 CSS pixels, and that the navigation dock stays outside that region at each viewport. The 720px width approximates the layout viewport at 200% zoom on a 1440px display; it is not a real browser zoom test.

The companion live API test uses a freshly migrated PostgreSQL database for registration, onboarding, weight, conversations, food/meal logging, editing, exports, and deletion. The same authenticated journey runs axe against the profile (including meal-reminder controls) and Help page; no WCAG 2/2.1 A/AA violations were reported there. Analytics coverage switches through 7, 30, and 90 days; the 90-day horizontally scrollable chart is keyboard-focusable, moves with the arrow key, and passes axe. The journey also tests alternate food-log dates, an empty day, then a return to a persisted day. It checks both document and scrolling-main reflow at 320, 390, 720, 768, and 1440 pixels across the exercised routes and asserts the dock remains in its separate row. Local Chromium screenshots are captured at 390 and 1440 pixels for each route visited in the authenticated flow; a complete comparison of every screenshot against all ZIP references is still outstanding.

## Remaining verification

Automated axe checks do not prove complete accessibility. Screen-reader behavior, actual browser zoom, all dialog/form error states, the configured scanner review, assistant provider responses, and every screen variant still need broader verification. The in-app browser currently blocks direct observation of `http://127.0.0.1:5173` due to a saved user permission; do not use another browser or direct automation as a workaround. No blanket WCAG conformance is claimed.

The welcome page additionally passed axe and 320/390/720/768/1440px reflow checks. Reduced-motion startup animation is disabled, and the branded loader disappears when the real session check completes. Desktop and mobile welcome screenshots were visually inspected. A source-level JSX regression test also rejects hard-coded placeholder links and click-handled buttons without an explicit `type`.
