# LossFit

LossFit is a nutrition tracking application being built from the supplied screen references. The UI reference assets live under `references/` and are intentionally excluded from Git.

## Local Windows setup

1. Install Python 3.12 and PostgreSQL 18.
2. Run `powershell -ExecutionPolicy Bypass -File .\scripts\setup-windows.ps1`. It creates `.venv`, installs pinned Python and npm dependencies, downloads Node 22.23.4 only if missing and verifies the checked-in SHA256, creates `.env` with unique local signing/deletion secrets if absent, starts the isolated project database on port 55432, and applies migrations. Keep the generated deletion-ledger key stable while retained backups may need replay.
3. On first setup, add the shared food catalogue with `powershell -ExecutionPolicy Bypass -File .\scripts\setup-windows.ps1 -ImportFoods`; the command is safe to rerun and imports the pinned USDA releases.
4. Run `scripts/start-dev.ps1`. Frontend is at `http://127.0.0.1:5173`; API at `http://127.0.0.1:3001/docs`.

The initial migration was applied to an empty local database. The application schema is maintained through versioned Alembic migrations and is covered by fresh-database tests. The provisioned production database is still empty; production migrations cannot run until its connection credentials are configured.

Password reset is enabled only when `SMTP_HOST` and `SMTP_FROM` are set. Configure an SMTP relay with `SMTP_SECURITY=ssl` (typically port 465) or `SMTP_SECURITY=starttls` (typically port 587), credentials where required, and `APP_BASE_URL` for the reset link. TLS certificates and hostnames are verified against the system trust store. Without SMTP, the endpoint returns the same privacy-preserving response but cannot deliver a reset email.

Google account linking is optional. Set backend-only `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and `GOOGLE_REDIRECT_URI`; register that exact callback URI in Google Cloud Console. For local development, the callback is `http://127.0.0.1:3001/api/v1/auth/google/callback`. Without all three values, the connected-accounts screen clearly reports that Google linking is unavailable.

Authentication returns a 20-minute access token held only in frontend memory. A rotating 30-day refresh token is stored as a hash in PostgreSQL and sent in an HttpOnly, SameSite=Lax cookie scoped to `/api/v1/auth`; production sets `Secure`. Refresh and logout require the readable double-submit CSRF token and an allowed `Origin`. For 30 seconds after rotation, the previous token can recover the same encrypted current token if navigation aborts the response; the ciphertext has a cryptographic 30-second expiry, and replay cannot create another token or extend the window. A browser-wide Web Lock serializes refreshes across same-origin tabs. To configure a separate test database, set `DATABASE_URL` for both Alembic and pytest before running them; do not point tests at a production database.

Run repeatable API tests with `scripts/test.ps1` after the isolated PostgreSQL cluster is running. The script creates a uniquely named database, applies all migrations, runs the suite, and retains that database so failures can be inspected.

Frontend tests run with `npm.cmd test` from `frontend/`. The Chromium browser smoke flow runs with `npm.cmd run test:e2e`; it starts Vite on port 4173 and expects Google Chrome Stable to be installed. This browser flow stubs API responses to verify the signed-out redirect, login return path, and layout overflow at 390px, 768px, and 1440px. For browser-to-API persistence, run `npm.cmd run test:e2e:local`; it creates a fresh temporary PostgreSQL database, migrates it, starts the API, Vite, and deterministic local vision/Open Food Facts fixtures, tests registration through meal reload, meal-photo and barcode scanners, manual nutrition-label entry, and persisted assistant replies/history/deletion, then drops only its uniquely named temporary database. These fixtures verify app behavior against deterministic provider-shaped responses; they do not replace live provider checks. Start the isolated PostgreSQL cluster first.

Reviewed nutrition documents are curated in `backend/knowledge/sources.json`; ingest them with `.venv/Scripts/python.exe scripts/ingest-knowledge.py` after migrations. Each source version is immutable: edit the text only when you also increase its version. Set backend-only `EMBEDDING_MODEL` alongside the AI provider URL/key to create embeddings. Without that setting the portable lexical retrieval adapter is used. The assistant supplies source markers and links from retrieved chunks and is instructed to abstain on unsupported general nutrition claims. Live provider answers and embeddings still require separate verification.

Populate the shared food catalogue with `.venv/Scripts/python.exe scripts/import-foods.py` after migrations. This pins and SHA-256 checks the USDA Foundation Foods October 2026 release and FNDDS 2021–2023 release, imports preparation variants and measured household portions, and retains FDC IDs and source links. Analytical Foundation values are marked verified; calculated Foundation and FNDDS values are marked reviewed. Negative or non-finite nutrient values are left unavailable with an explicit note; nutrients absent from a source remain null. Branded Foods are not included. The data archives are cached under ignored `.local/cache/` and can be downloaded again by the importer.

Packaged-food barcode lookup uses the Open Food Facts v3 product API with a project User-Agent and rate limits. Imported products are private to the requesting account, deduplicated by barcode, carry their product/source URLs and per-nutrient imported status, and are visibly identified as community-contributed and not independently verified. The UI links to each source record; see the [Open Food Facts data license guidance](https://openfoodfacts.github.io/documentation/docs/Product-Opener/api/tutorials/license-be-on-the-legal-side/) for the database ODbL and individual Database Contents License. Barcode lookup accepts checked GTIN-8/UPC-A/EAN-13/GTIN-14 codes; nutrition reported per 100 ml is not converted to grams. Live service behavior should be verified before deployment. The nutrition-label workflow supports AI-assisted extraction through the backend-configured vision provider, plus manual transcription when unavailable. Photos are resized and stripped of metadata, forwarded to the provider, and not retained by LossFit. The user reviews and can edit every extracted field before saving. Basis is explicitly selected, missing nutrients remain null, and server-side conversion creates user-provided nutrition. Automated tests use a deterministic provider; live label OCR remains unverified.

Account deletion removes the account's application records in one database transaction and records a keyed email digest in a restricted ledger. Failed private-file removals remain in the internal cleanup queue; retry them with `.venv/Scripts/python.exe scripts/cleanup-private-files.py`. Configure vision credentials in backend-only `AI_BASE_URL`, `AI_API_KEY`, and `VISION_MODEL` values to enable the photo scanner. Personal food photos are stored outside public assets, fetched through authenticated owner-scoped routes, and removed on replacement, deletion, or account deletion. A restore procedure must replay a separately preserved deletion ledger against restored user tables before serving traffic. Database backups may retain old personal data until their configured retention expires; the ledger is intended to prevent those restores from reactivating deleted accounts.

## Production operations

See [deployment and monitoring](docs/deployment.md) for the production environment template, fail-closed HTTPS/secret checks, sanitized JSON request events, production launcher, reverse-proxy template, and verification gates. The frontend is deployed at [lossfit-oa1h.vercel.app](https://lossfit-oa1h.vercel.app); its API health route currently fails because production `DATABASE_URL` is not configured. Production data workflows and an external alert destination have not been verified.

Set `ENVIRONMENT=production`, a random secret, HTTPS origins, restricted CORS, provider credentials only in the backend secret store, and private upload storage outside the web root. Enable database backups with `pg_dump -Fc`; restore to an isolated database with `pg_restore --clean --if-exists`. Establish encrypted offsite retention and deletion-ledger replay before production. Configure error monitoring with request-body and credential scrubbing.

See [backup and restore procedures](docs/backup-restore.md) for Windows PowerShell commands, protected deletion-ledger export, dry-run review, replay, and private-file cleanup.
